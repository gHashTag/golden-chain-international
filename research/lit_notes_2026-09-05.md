# Torn write prevention on Amazon EC2 Linux instances

**URL:** https://docs.aws.amazon.com/AWSEC2/latest/UserGuide/storage-twp.html

- Torn write prevention is supported with Linux instances only.

- Torn write prevention is a block storage feature designed by AWS to improve the performance of your I/O-intensive relational database workloads and reduce latency without negatively impacting data resiliency.

- Relational databases that use InnoDB or XtraDB as the database engine, such as MySQL and MariaDB, will benefit from torn write prevention.

- Typically, relational databases that use pages larger than the *power fail atomicity* of the storage device use *data logging* mechanisms to protect against torn writes.

- MariaDB and MySQL use a *doublewrite buffer* file to log data before writing it to data tables.

- In the event of incomplete or torn writes, as a result of operating system crashes or power loss during write transactions, the database can recover the data from the doublewrite buffer.

- The additional I/O overhead associated with writing to the doublewrite buffer impacts database performance and application latency, and it reduces the number transactions that can be processed per second.

- With *torn write prevention*, data is written to storage in *all-or-nothing* write transactions, which eliminates the need for using the doublewrite buffer.

- This prevents partial, or torn, data from being written to storage in the event of operating system crashes or power loss during write transactions.

- The number of transactions processed per second can be increased by up to 30 percent, and write latency can be decreased by up to 50 percent, without compromising the resiliency of your workloads.

## Crash atomicity

- “The action atomicity ensures that all non-volatile storage modifications performed as part of the received message handling are *failure atomic* [9], i.e., their effects are either persisted in their entirety or not at all.”

## Rollback of persistent or non-volatile state

- “However, the protection offered by a TEE only applies during program execution. Once power is switched off, the non-volatile portion of the program state becomes vulnerable to *rollback* attacks wherein it is undetectably reverted to an older version.”

- “However, a TEE is a not a panacea, because the protection it offers only applies during program execution. Once power is switched off, the non-volatile portion of the program state becomes vulnerable to tampering by an attacker.”

- “To address this, hardware manufacturers provide a *sealing* mechanism [12] that allows programs to encrypt a portion of their state using a device-specific key before storing it in non-volatile storage.”

- “When the machine restarts, the TEE can check whether the sealed state was indeed written by it in the past. However, it cannot determine whether this state is the most recent version.”

- “This limitation makes TEE-based systems vulnerable to *rollback* attacks where the sealed state is undetectably replaced with an older version [35, 40, 8, 42, 13].”

- Under the crash-restart-rollback (\(\mathsf{CRR}\)) model, “a replica can experience a *crash* that interrupts its execution either permanently or temporarily.”

- “Upon restart, a replica with non-volatile storage may additionally experience a *rollback* failure, which causes the content of its non-volatile storage to revert to a version older than it had before the latest crash.”

- A \(\mathsf{CRR}\)-faulty process “can permanently crash, crash and restart infinitely often, or crash and restart with the content of its non-volatile storage being undetectably reverted to an older version.”

- Replica classifications explicitly include:
  - “a replica is *rollback-faulty* if it rolls back at least once.”
  - “Perfect and benign replicas are together called *correct*; crash-faulty and rollback-faulty replicas are together called *faulty*.”

- “The classical crash-recovery failure model assumed that every process is equipped with durable storage that cannot be rolled back [22].”

- “In contrast, in our \(\mathsf{CRR}\) model a recovering process cannot trust its non-volatile storage to be up-to-date, leading to different resilience bounds.”

## Non-volatile storage and durability requirements

- “To study tradeoffs between failure resilience and non-volatile storage consumption, we assume that \(s\geq 0\) replicas have access to non-volatile storage.”

- **Theorem 1:** “Assume that all replicas have access to non-volatile storage. Then for all \(k,r,b\), there exists a \(\mathsf{CRR}(k,r,b)\)-tolerant implementation of a wait-free atomic MWMR register if and only if \(n\geq 2k+\min(b,r)+1\).”

- “Since this storage is not protected by TEEs, in practice applications must rely on expensive mechanisms to monitor its integrity at runtime, e.g., using TEE-protected integrity metadata, such as Merkle trees.”

- **Theorem 2:** “Let \(s\) be the number of replicas with non-volatile storage. Then for all \(k,r,b\), there exists a \(\mathsf{CRR}(k,r,b)\)-tolerant implementation of a wait-free atomic MWMR register if and only if”
  \[
  (2k+r+1\leq n<2k+b+1\ \wedge\ s\geq 2k+r+1)\ \vee\ (n\geq 2k+b+1).
  \]

- “The above theorem shows that, when \(n\geq 2k+b+1\), atomic registers can be implemented without any stable storage at all.”

- “In practice, avoiding non-volatile storage offers substantial performance gains when the register state fits within the TEE-protected RAM, as it avoids the overheads of monitoring storage integrity at runtime.”

- Algorithm \(\mathcal{A}_1\):
  - “keeps the state of \(2k+r+1\) replicas in non-volatile storage, which is the minimum required by the lower bound of Theorem 2.”
  - Its restart handler “returns immediately,” and “the \({\sf stale}\) flag is always false at all replicas.”

- Algorithm \(\mathcal{A}_2\):
  - “does not use non-volatile storage.”
  - When \(n\geq 2k+b+1\), “atomic registers can be implemented without any stable storage at all.”

- The dynamic register algorithm TEE-Rex:
  - “requires neither durable storage nor specialized hardware, such as trusted monotonic counters.”
  - “Since under \(\mathsf{CRR}\text{-}\mathsf{D}(d,c,M)\), any number of replicas can suffer rollbacks in some executions, the algorithm does not rely on non-volatile storage.”
  - “It also does not require the knowledge of \(c\).”

## Recovery and persistent-state reconstruction

- “The most interesting ingredient of TEE-Rex is a novel distributed recovery protocol that enables crashed replicas to rebuild their state and become fully operational upon restart.”

- “Since replicas lose their memory contents during a restart, TEE-Rex follows the approach of \(\mathcal{A}_2\): a replica relies on its \({\sf stale}\) flag to determine whether its current state can be used to respond to \({\tt READ}\) requests.”

- “The protocol achieves this by synchronizing with other replicas.”

- “However, doing this naively by simply querying a read quorum and adopting the state of the most up-to-date replica would lead to a safety violation.”

- In the modified recovery procedure described in Example 9:
  - A restarting replica sets \({\sf stale}=\text{\sc true}\).
  - It invokes \({\tt read\texttt{\_quorum}}(\mathsf{TSVal})\).
  - It adopts the state with the highest timestamp.
  - It sets \({\sf stale}=\text{\sc false}\).
  - The described execution produces a linearizability violation because a completed write can later be lost from the state observed by a read.

- Example 9 explicitly states:
  - “Replica \(p_{3}\) gets \(m\) first, sets \(\mathsf{state}=((1,4),v)\), and responds with a \({\tt WRITE\texttt{\_ACK}}\). It then crashes, loses its state, and reconstructs the state by contacting a read quorum \(\{p_{1},p_{2}\}\) of size \(q_r=d+1=2\). Since \(m\) has not yet reached either replica, \(p_{3}\) sets \(\mathsf{state}\) back to its initial value \(((0,0),v_0)\).”
  - A later read “returns \(v_0\), violating linearizability.”

- “To address the above problem, the set of responses collected by \(p_4\) from a write quorum of replicas must be *crash-consistent* [36].”

- TEE-Rex recovery:
  - Sets \({\sf stale}\) to true, preventing the replica from replying to \({\tt READ}\) and \({\tt WRITE}(\mathsf{TSVal})\) messages.
  - Selects a new incarnation number.
  - Stores it at a write quorum.
  - Invokes \({\tt read\texttt{\_quorum}}(\mathsf{State})\) to retrieve register states and crash vectors.
  - Reconstructs its state by merging crash vectors and selecting the register value with the highest timestamp.
  - Clears the \({\sf stale}\) flag.

- “The new incarnation number is written to a read quorum of replicas, which intersects any write quorum that may be used by a concurrent invocation of \({\tt write\texttt{\_quorum}}(\mathsf{TSVal})\). This ensures that this invocation only accepts a crash-consistent set of responses.”

- “When recovering, \(p_2\) will reconstruct its crash vector to a value no lower than what it was before the crash.”

- “This is ensured by the fact that each recovering replica, such as \(p_3\), writes its incarnation number crash-consistently to a write quorum (line 10), which intersects with a read quorum that a replica such as \(p_2\) uses to reconstruct its state during recovery (line 11).”

## Security and freshness claims that require additional mechanisms

- TEE sealing provides encryption with a device-specific key and allows the TEE to verify that sealed state “was indeed written by it in the past,” but:
  - “it cannot determine whether this state is the most recent version.”
  - Consequently, sealing alone does not prevent undetectable rollback to an older sealed state.

- “Since this storage is not protected by TEEs, in practice applications must rely on expensive mechanisms to monitor its integrity at runtime, e.g., using TEE-protected integrity metadata, such as Merkle trees.”

- Incarnation Number Monotonicity is stated as:
  - “Assume that a replica \(p_i\) sets \(\mathsf{state}.\mathsf{cv}[i]\) to \(g\) at line 9 at time \(t\). Then \(g>0\) and for all times \(t'>t\), if \(p_i\) sets \(\mathsf{state}.\mathsf{cv}[i]\) to \(g'\) at line 9 at time \(t'\), then \(g'>g\).”

- “This property can be easily ensured assuming that each replica has a built-in monotonic counter that is never rolled back, as done in previous work [36].”

- TEE-Rex instead ensures the property “without such an assumption” through a distributed mechanism:
  - Each replica’s state includes \(\mathsf{cv}\) and \(\mathsf{pre\texttt{\_}cv}\).
  - Before assigning a new incarnation number to \(\mathsf{state}.\mathsf{cv}[i]\), the replica writes it to \(\mathsf{state}.\mathsf{pre\texttt{\_}cv}[i]\) at a crash-consistent write quorum.
  - Upon restart, it restores the previous incarnation number using the maximum of responses from \({\tt read\texttt{\_quorum}}(\mathsf{preCV}(i))\), then increments the result.
  - “The intersection between the quorums used by \({\tt write\texttt{\_quorum}}(\mathsf{preCV})\) and \({\tt read\texttt{\_quorum}}(\mathsf{preCV})\) helps ensure Property 11.”

- “In [26, §B] we prove that, even though the above mechanism may require processes to temporarily adopt stale incarnation numbers, it does ensure Incarnation Number Monotonicity (Property 11).”

- “Since in the presence of rollbacks the replicas cannot rely on non-volatile storage to implement monotonically growing incarnation numbers, TEE-Rex relies on a distributed mechanism for this purpose.”

- “A replica cannot restore its previous incarnation number by just reading it using \({\tt read\texttt{\_quorum}}(\mathsf{CV})\): if the replica crashed before completing the \({\tt write\texttt{\_quorum}}(\mathsf{CV})\) at line 10, the \({\tt read\texttt{\_quorum}}\) is not guaranteed to restore its latest pre-crash incarnation number, thus violating Property 11.”

- Persistent monotonic hardware counters:
  - “Persistent monotonic hardware counters have been demonstrated in [40] to be a powerful mechanism to guard against rollback attacks.”
  - “In TEE-based systems they can be used together with sealing (§1) to validate state freshness upon restart [12].”
  - “Unfortunately, these solutions inherit the drawbacks of persistent counters.”
  - Their drawbacks include:
    - “These counters are implemented using flash memory, resulting in poor write performance and quick wear-out [35].”
    - “Furthermore, they are not universally supported by TEE manufacturers, and have been recently deprecated by Intel SGX [23].”

## https://arxiv.org/abs/2511.13641
# It's a Feature, Not a Bug: Secure and Auditable State Rollback for Confidential Cloud Applications

**Source URL:** https://arxiv.org/abs/2511.13641

- Replay and rollback attacks threaten cloud application integrity by reintroducing authentic yet stale data through an untrusted storage interface to compromise application decision-making.
- Prior security frameworks mitigate these attacks by enforcing forward-only state transitions (state continuity) with hardware-backed mechanisms.
- Prior security frameworks categorically treat all rollback as malicious and thus preclude legitimate rollbacks used for operational recovery from corruption or misconfiguration.
- Rebound is a general-purpose security framework that preserves rollback protection while enabling policy-authorized legitimate rollbacks of:
  - Application binaries
  - Configuration
  - Data
- Rebound includes a reference monitor that:
  - Mediates state transitions
  - Enforces authorization policy
  - Guarantees atomicity of state updates and rollbacks
  - Emits a tamper-evident log that provides transparency to applications and auditors
- The paper formally proves Rebound’s security properties.
- An application case study with software deployment workflows in GitLab CI shows that Rebound enables robust control over:
  - Binary versioning
  - Configuration versioning
  - Raw data versioning
- The case study reports low end-to-end overhead.
