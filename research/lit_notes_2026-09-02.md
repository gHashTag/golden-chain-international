# Literature note - 2026-09-02 - W-INTL-269

The literature search ran in parallel with implementation of
`research/sliding_window_freshness.py`. The question was whether a bounded
sliding-window acceptance rule around the keyed helper frame is a new protocol
contribution or a standard replay-control boundary.

## Directly checked sources

- [Beyond Message Passing: A Semantic View of Agent Communication Protocols](https://arxiv.org/abs/2604.02369), arXiv:2604.02369v3, Dun Yuan, Fuyuan Lyu, Ye Yuan, Weixu Zhang and co-authors. The abstract describes freshness and replay resistance as transport-layer responsibilities, so it is a systems boundary, not evidence of a new cryptographic primitive here. Metadata was checked through the arXiv API on 2026-09-02.
- [A lightweight PUF-based authentication protocol](https://arxiv.org/abs/2405.13146), arXiv:2405.13146v1, Yu Zhuang and Gaoxiang Li. The abstract places protocol design around PUF authentication and resource constraints. It is prior art for the surrounding protocol setting, not a claim that this finite control is secure. Metadata was checked through the arXiv API on 2026-09-02.
- [IPsec Anti-Replay Algorithm without Bit Shifting](https://www.rfc-editor.org/rfc/rfc6479), RFC 6479, X. Zhang and T. Tsou, January 2012. The RFC explicitly describes a sliding anti-replay window with a high sequence boundary and a bitmap, including out-of-order acceptance inside the window. This makes the mechanism prior art and fixes the right interpretation of this loop: a bounded reproduction/control, not protocol novelty.
- The already checked [PUF authentication review](https://pmc.ncbi.nlm.nih.gov/articles/PMC11487452/) keeps replay and freshness as protocol threat boundaries, while [robust fuzzy extractors](https://arxiv.org/abs/2405.04021) treat helper-data tamper detection as a separate robustness property. Neither source supplies a deployment claim for this repository.

The page reader timed out on the three direct pages in this run, so the arXiv titles, authors, versions, and abstracts above were taken from direct arXiv API metadata after that failure. No fresh 2025-2026 paper was found that makes the sliding-window mechanism a distinct contribution. The result is therefore intentionally framed as an implementation control with standard prior art.

## What is measured

[measured] With seed 20260902, 64 trials, an eight-sequence bitmap window, the control accepts 64/64 in-order frames and 64/64 unseen in-window out-of-order frames. It rejects 64/64 duplicate frames, 64/64 sequences exactly eight positions behind the high-water mark, 64/64 sequence mutations without a recomputed tag, 64/64 wrong-key frames, and 64/64 truncated frames.

[proved] In this finite verifier, tag and inner-frame checks run before the bitmap changes. A valid unseen sequence within the declared window is accepted once; a duplicate bit or a sequence outside the window is rejected.

[open conjecture] The bitmap width is a test parameter, not a deployment recommendation. Rollback-resistant storage, distributed ordering, loss recovery, key management, leakage, active attackers, side channels, area, timing, FPGA behaviour, and the G16 three-node shared-uplink demonstration remain unmeasured.
